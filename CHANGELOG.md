# Changelog

All notable changes to cornfield. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- The first commit: cornfield extracted from the topology tool of a private monorepo.
  - The explorer: the WebGL2 map with its Canvas 2D fallback, orbit, data-flow and House views, labels, search, layers, the bench (`/?bench=1`, `/?fixture=5k`).
  - Proposals: the format and its validator, Before / Diff / After, the scenario player, what-if edits, Approve / Send back (kept in cornfield's data folder until v1 posts them to the spec PR).
  - Personas, the cloud registry and its detectors, outage scenarios, the House view over a house source.
  - The deriver contract (version 1) and three derivers: `starter` (npm workspaces, modules and imports), `personas`, `cloud`.
  - The CLI: `serve`, `sync`, `validate`, `status`, `proposal`, `review`.
  - The server: an allowlist, never a folder; a strict Content-Security-Policy; loopback only until forge sign-in exists.
  - A Dockerfile, `compose.example.yml`, GitHub Actions for tests, secret scanning and (inert until switched on) releases.
- The SQLite store (`server/db.js`, #2): `cornfield.db` in the data folder over Node's built-in `node:sqlite`, numbered migrations, and the four tables of v1: `sessions`, `reviews`, `actions`, `forge_cache`.
- Sign-in and the admins-only guard (`server/auth.js`, #5): GitHub or Forgejo OAuth (with PKCE and a signed state), sessions in `cornfield.db` (the cookie's value hashed, the forge token encrypted), the permission asked again every 15 minutes, the sign-in and "ask a maintainer" pages, Sign out in the header, and the guard on every route but `/healthz`. With sign-in configured and an https public URL the server may listen beyond loopback; without, it still refuses. Setting up an OAuth app on each forge: `docs/sign-in.md`.
- The forge interface and the GitHub adapter (`server/forge.js`, `server/forge-github.js`, `server/forge-http.js`, #3): who is signed in and their permission, issues, pull requests and their files, comments, checks, re-running a failed Actions job, landing a green pull request at the head its checks ran on, branches, a file at a ref; pagination, rate limits and errors in plain words. Tests run against recorded answers and a fake forge.
- Proposals from spec PRs (`server/proposal-pulls.js`, #6): with sign-in, the Proposals menu lists the open pull requests that add or change a file in the proposals folder beside the checkout and the worktrees, names the PR, and reads each file at the PR's head commit with the signed-in maintainer's own token. A PR that deletes a proposal lists none; a forge that cannot be asked is said plainly above the list. Without a forge nothing changes.
- The issues and PRs panel (`explorer/forge-panel.js`, `server/forge-routes.js`, #8): with a forge in the config and a maintainer signed in, a header button opens a panel of the repo's pull requests and issues with filters (state, label, author, search), links out to the forge, and rate limits and errors in plain words. Selecting a pull request asks for its files and checks and lights the nodes the files are (the deepest `file` that holds each; a file on no node is listed as not on the map) and the tests a failing check names; the rest of the map fades back. The server side is read-only: `GET /api/forge/issues`, `/pulls` and `/pulls/<n>`, behind the sign-in guard, as the signed-in maintainer with their own token, cached per user for a minute in `forge_cache` with an ETag (the last answer is served, marked old, while the forge is rate-limited). A bottom sheet on a phone, a slide-over from the left from 768px; keyboard reachable, announced through the map's live region, inert when closed, in light and dark. With no forge in the config nothing appears. Guide: `docs/issues-and-prs.md`.
- Reviews are PR comments (`server/reviews.js`, #7): Approve and Send back on a proposal of a spec PR post a comment as the signed-in maintainer, a human line and a fenced `cornfield-review <slug>` block holding `{ verdict, note, edits }`, and write the `actions` audit row; the latest comment by an admin (admin or maintain) is the review, and a reader's block, a malformed or quoted one is ignored. `cornfield review <slug>` reads it from the PR (`CORNFIELD_FORGE_TOKEN`, or `GITHUB_TOKEN`; `--pr <n>`). Reviews Stage 1 kept in the data folder are posted once on the one open spec PR that holds their proposal and renamed `.migrated`; the data-folder path is gone, so a draft in the checkout or a worktree, with no PR, cannot be reviewed until it is pushed as a spec PR.
- Safe actions (`server/forge-actions.js`, `explorer/forge-panel.js`, CF-08): from a selected pull request a maintainer can land a green one (the forge's own merge by the config's `forge.mergeMethod`, at the head its checks ran on, once at least one check passed and the forge says it is ready: on GitHub `mergeable_state` clean and no workflow still running) and re-run a failed or cancelled check, and nothing else: no force-merge, no deploy. `POST /api/forge/pulls/<n>/merge` and `/rerun` are same-origin, JSON, signed-in maintainer only, with the permission asked of the forge at that moment; the server reads the pull request and its checks again (open, not a draft, every check green, the head is the one the page showed, else 409), refuses a double click (one at a time, a few seconds apart, 20 a minute), and writes every attempt, refused or failed or done, to the `actions` table before anything is asked of the forge. The panel's Land it opens a confirm dialog showing the pull request, its head commit, where it goes and each check (focus held, Escape cancels, announced); a failed check has Re-run where the forge can run it again, and the panel says why where it cannot. Guide: `docs/issues-and-prs.md`.
- Agents, tracked (`explorer/agents-model.js`, #10, ADR 0007): the issues and PRs panel has an Agents tab that groups branches, spec PRs and pull requests by the issue ("Closes / Fixes / Resolves #n" in the text, or its number in the branch name) and the proposal (the spec PR, or its slug in the branch name) they belong to, with what links to neither in a group of its own, and marks the work agents made and why. What counts as an agent is the config's new `agents` key (`authors`, `labels`, `branchPrefixes`, and `bots`, on by default: a `[bot]` login or the forge's Bot type), empty by default and validated. One more read-only route, `GET /api/forge/work`, behind the sign-in guard and cached like the others; pull requests now carry their text. Nothing is launched. Switches for agent-made only and for merged and closed work; keyboard reachable, announced, in light and dark, and in the phone sheet. Guide: `docs/agents.md`.
- Deploys on the map (`server/deploys.js`, `explorer/forge-panel.js`, PIPE-03, #16): a read-only `runs({ limit })` on the forge interface, in both adapters (GitHub Actions workflow runs; Forgejo Actions runs from Forgejo 11 and Gitea 1.24, said in words, with a 501, where an instance cannot list them) and in the shared contract test, and `GET /api/forge/deploys`. A new `deploys` key in `cornfield.config.js` says which workflows are deploys (default `*deploy*`) and which map nodes each restarts (ids or labels; a stack brings its containers). The panel's new Deploys list shows the latest deploys with their state, branch, commit and who started them; selecting one lights the nodes it restarted (red when it failed) through the paint pull requests use, turning on the layers those nodes are on. A deploy no pattern names is listed, not dropped. Nothing is ever deployed, re-run or cancelled. Guide: `docs/deploys.md`.
- Release notes from the map (`core/release-notes.js`, `server/release-notes.js`, PIPE-04): the pull requests merged since the last version tag (or a tag you choose), grouped by what they changed on the map: a pull request is listed under each area (the app or package below the root) it touched, with the nodes it changed; one that touches nothing on the map is under "Other"; one with the `breaking` label (`releaseNotes.breakingLabel` in the config) is under "Breaking", first. Each line links its pull request, and the same inputs always give the same Markdown. The forge interface gains `tags()`, `tag(name)` and `createReleaseDraft({ tag, name, body })` in both adapters and the shared contract test. In the issues and PRs panel a Release notes tab previews the draft, copies it (the clipboard, else the text selected), and, after a confirm step, posts it as a **draft** release: `POST /api/forge/release-drafts`, the only write of the panel, same-origin and for a signed-in maintainer asked about again at that moment, with a row in the audit (`actions`) before the forge is asked. It never publishes a release and never makes or pushes a tag. `cornfield notes [--since <tag>]` prints the Markdown (read-only, with `CORNFIELD_FORGE_TOKEN`). Guide: `docs/issues-and-prs.md`.
- The `docs` deriver: a repo's Markdown on the map as an app with a page per document, its links to other docs and to the code they describe; a broken link fails `validate`.
- Foreign `Host` headers are refused (`server/bind.js` `hostAllowed`, #47): a request whose `Host` is not a loopback name (or, with sign-in, the public URL's host) is a 421 on every route, `/healthz` included, before the guard and the proxies, so DNS rebinding cannot read the map from a user's browser. See `docs/sign-in.md`.
- `cornfield docs`: the docs as a small static site built from that map (a page per document, the links around it, a map of the docs' links), published for cornfield itself to GitHub Pages by `.github/workflows/pages.yml`.
- The deriver kit, `cornfield/deriver-kit`: the deriver contract as JSDoc types, `defineDeriver`, and a test kit (`fixtureRepo`, `runDeriver`, `checkDeriver`) that runs a repo's own deriver on a fixture repo as `sync` and `validate` would and lists everything `validate` would fail on. Guide: `docs/deriver-kit.md`.
- The `compose` deriver: stacks and containers from Docker compose files, and an app with a `runs-on` edge per host a Caddyfile or Traefik labels route to them (SRC-02). The sample repo's stack now comes from its compose file.
- The `openapi` deriver: an API's endpoints from its OpenAPI, Swagger or OpenCollection file, as page nodes with their methods under the API's app (SRC-05). `test/fixtures/openapi` is a repo with nothing but an OpenAPI file.
- The starter deriver reads Python packages, Go modules and Rust crates the way it reads npm workspaces: their manifests, the imports between them, and a dependency declared and never imported (SRC-04). A fixture repo per language in `test/fixtures/python`, `go` and `rust`.
- Light mode (MAP-01): the explorer follows the system's light or dark setting, and a toggle in the header steps through system, light and dark (kept in the browser; `?theme=light|dark` for one visit). Both renderers and the labels draw the light map, its colours derived from the dark ones: the same hues, deepened to at least 3:1 on the light ground (4.5:1 for text).
- Keyboard and screen readers (MAP-02): the map takes the focus and its keys (arrows pan, + and - zoom, 0 fits, N and P step through the nodes, Enter and Escape go into and out of the panel, Alt+arrow moves a node in Freeform); a live region says where the keyboard landed; Enter in the search selects the match; a what-if edge can be drawn from a list. The closed panel is inert, the menus say whether they are open, and the page has its landmarks and heading. axe-core (a dev dependency) checks each state of the page in the tests. [docs/accessibility.md](docs/accessibility.md).
- The `world` deriver: the machines of `stacks/world.json` (hostnames only, never an address) as machine nodes, with `runs-on` edges from the stacks and packages that run on them and from a virtual machine to its host, and the tailnet detector of the `cloud` deriver reads the machines that joined the tailnet (SRC-03). Opt-in: it is not in the default derivers.
- Home Assistant as a house source (SRC-01): with `CORNFIELD_HA_URL` and `CORNFIELD_HA_TOKEN` set, the server reads the floor, area, device and entity registries over the WebSocket API (read-only) and serves them as the house answer; areas map to a house file's rooms by name and alias, and a `mobile_app` device (a person's phone) is left out entirely. The token never leaves the server.
- Always on (CF-10): `compose.example.yml` with sign-in (public URL, forge OAuth pair and session secret from the environment, a missing one stops `compose up`, the port published on loopback for the reverse proxy, a read-only non-root container), the image's health check on `/healthz`, and [docs/deploy.md](docs/deploy.md): Caddy and Traefik examples, forwarded headers (cornfield trusts none), the data volume's permissions, security notes, rotating the session secret, backup. The image smoke test now also checks the user, the data folder, the health check and the compose file.
- Mockups beside a proposal (PIPE-02, #15): a proposal may list `mockups`, screens (png, jpg, webp, svg or html) kept beside it in the spec branch, each with the `node` it belongs to, a `path` inside the proposals folder and a `title`. `validate` holds the path inside the folder and the node to one the proposal touches. A node's panel lists its mockups, and each opens in a window over the map (the title is the alt text; keyboard and screen reader are covered). They come from the checkout, the worktrees and open spec PRs (read at the head commit; `fileBytes` joins the forge interface). HTML and SVG are untrusted: every mockup is served with `Content-Security-Policy: sandbox; default-src 'none'`, `nosniff` and a same-origin frame policy, and the explorer shows HTML in an `<iframe sandbox>` with nothing allowed and SVG as an image. Approving a spec PR's proposal records each mockup's SHA-256, as the server reads it at the head, in the review comment's block (`mockups`), so a file changed afterwards reads "Changed since you approved"; `validate` also fails when a listed file is not there.

### Changed

- `sync` takes away an edge of a derived kind only for the deriver that emits that kind, at the end where it puts its own nodes (`madeBy` and `claims` from `deriveTopology`), so a hand-written edge into a derived node of another deriver stays.
- A container's `selfHosted` and `summary` are hand-written, no longer fields the code decides.
- Node 22.13 or newer (`engines.node`, was 22.5): the SQLite store runs on `node:sqlite` without a flag only from 22.13, and sign-in is its first user. The image (`node:22-alpine`) and CI (`node-version: 22`) already run a newer 22.
- The Forgejo adapter (`server/forge-forgejo.js`, #4) behind the same interface and the same contract tests, over Forgejo's v1 API (Gitea-compatible): its token header, its three permission levels (its admins are the maintainers), issues and pull requests through `Link` paging, Actions results read as commit statuses, landing a green pull request at the head its checks ran on. Forgejo's API cannot re-run a check, so none is `rerunnable`. Tests run against hand-written recorded answers and a fake forge.
