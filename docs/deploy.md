# Deploy: cornfield always on

The Docker image is the always-on dashboard: forge sign-in in front of every route, a reverse proxy that ends TLS, and one named volume for cornfield's own state. [compose.example.yml](../compose.example.yml) is all of it as one service; this page says what each part is for.

## What you need

1. An OAuth app on your forge, with the public URL's `/auth/callback` as its callback ([sign-in](sign-in.md)).
2. A name and a certificate: a reverse proxy (Caddy and Traefik below) that ends TLS for `https://cornfield.example.org`.
3. A `.env` file beside the compose file, **not committed**, with:

| Env | Where it comes from |
|---|---|
| `CORNFIELD_PUBLIC_URL` | the https origin people open, like `https://cornfield.example.org` |
| `CORNFIELD_GITHUB_CLIENT_ID`, `CORNFIELD_GITHUB_CLIENT_SECRET` | the OAuth app's page on the forge (`CORNFIELD_FORGEJO_*` for Forgejo, with the config's `forge.type`) |
| `CORNFIELD_SESSION_SECRET` | generated by you, once: `openssl rand -base64 48` (there is no default, and cornfield refuses a short one) |

Then `docker compose up -d`. A missing value stops compose and names it. The image holds none of these: they are read from the environment when the container starts. cornfield reads env only, so an orchestrator that mounts secrets as files has to export them into the environment first.

## The port and the address

The image listens on `CORNFIELD_PORT` (3350). In the image `CORNFIELD_HOST` is `127.0.0.1`, the container's own loopback, which a published port cannot reach; the compose file sets `0.0.0.0`. cornfield allows that only with sign-in configured and an https public URL and refuses to start otherwise, saying why ([sign-in](sign-in.md#where-it-may-listen)). The compose file publishes the port on the host's `127.0.0.1` only, so only the proxy on the same machine reaches it. If the proxy is a container, put both on one compose network and drop `ports`.

## Reverse proxy

TLS ends at the proxy, which talks plain http to cornfield over the private hop. The public URL is https, so the session cookie is `Secure` and `__Host-` prefixed.

**Forwarded headers.** cornfield does not read `X-Forwarded-For`, `X-Forwarded-Proto` or `X-Forwarded-Host`. Every URL it hands out (the OAuth callback, redirects) comes from `CORNFIELD_PUBLIC_URL`, and whether cookies are `Secure` is decided by that setting, not by a header. So there is nothing to trust and nothing to configure, and a client that sends a forged `X-Forwarded-*` changes nothing. Two things the proxy must do: pass the `Host` header through unchanged, and be the only way in. cornfield answers only a `Host` that is the public URL's host or a loopback name, and gives anything else `421 Misdirected Request`, against DNS rebinding ([sign-in](sign-in.md#which-host-it-answers)). Caddy and Traefik pass `Host` through by default; nginx does not, so add `proxy_set_header Host $host;` beside `proxy_pass`. The image's health check asks `127.0.0.1` from inside the container, a loopback name, so it keeps working. If cornfield ever starts trusting these headers, that is only safe behind a proxy that overwrites them.

Caddy (`Caddyfile`; it gets the certificate itself):

```
cornfield.example.org {
	reverse_proxy 127.0.0.1:3350
}
```

Traefik: the labels in the compose file's commented block: a router for the `Host` on the `websecure` entrypoint with a certificate resolver, and the service's `loadbalancer.server.port` set to `3350`.

## The data folder

`/data` is a named volume (`cornfield-data`) holding `cornfield.db`: sessions (with maintainers' forge tokens, encrypted), the audit of every review posted, the forge cache. The image creates `/data` owned by its non-root user `node` (uid 1000), so a new named volume is created owned by it; cornfield keeps the folder `0700` and the file `0600`. With a bind mount instead of a volume, `chown 1000:1000` and `chmod 700` the host folder first. The repo is mounted read-only at `/repo`. The container runs as `node`, with a read-only root filesystem, no capabilities and `no-new-privileges`.

The health check asks `GET /healthz`, which answers `{ "ok": true }` without a session; `docker ps` shows the container as healthy.

## Security notes

**Exposed:** the sign-in routes under `/auth/` and `/healthz` (`{ "ok": true }`, nothing else), to anyone who can reach the proxy. **Not exposed:** everything else (the page, `topology.json`, proposals, the API, the explorer's own files) answers 401 without a session and 403 to anyone who is not a maintainer of the configured repo ([ADR 0004](adr/0004-admins-only-loopback-until-sign-in.md)). There is no switch to open it.

- **Secrets** live in `.env` or your orchestrator's secret store, never in the image, the compose file or git. The OAuth client secret and the session secret are the two to protect; keep `.env` mode `0600`.
- **A maintainer's forge token** is kept encrypted in `cornfield.db`, with a key from the session secret. Whoever has both the file and the secret can use those tokens, so keep backups apart from `.env`.
- **Rotate the session secret** when it may have leaked, or on a schedule: put a new `openssl rand -base64 48` in `.env` and run `docker compose up -d`. Every session becomes unreadable, so everyone is signed out and signs in again. Rotate the OAuth client secret on the forge the same way and update `.env`.
- **Back up** the `cornfield-data` volume (it holds the sessions and the audit of what cornfield did on the forge). Stop the container for a consistent copy, then archive it, for example `docker run --rm -v cornfield-data:/data:ro -v "$PWD:/backup" alpine tar czf /backup/cornfield-data.tgz -C /data .`. A backup holds encrypted tokens and session hashes: store it like a secret. Restore by unpacking into an empty volume and `chown -R 1000:1000` it.
- **Updates:** pin the image to a version tag rather than `latest` once you depend on it.
