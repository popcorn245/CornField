# Spec 0001: cornfield v1

Status: approved by the maintainer in chat (2026-10-17), so it skips the map review gate ([ADR 0010](../adr/0010-cornfield-uses-its-own-gate.md)). Its proposal, [proposals/0001-v1.json](proposals/0001-v1.json), draws v1 on cornfield's own map and is the worked example of the format; it is deleted in the PR that lands the last v1 issue.

The why and the decisions are in [the vision](../vision.md); this spec is what v1 builds and how.

## 1. Where Stage 1 left it (the first commit)

Stage 1 is the extraction: everything below works today, on a laptop, on loopback.

| Part | Where | What it does |
|---|---|---|

| The formats | `core/schema.js`, `core/proposal.js`, `core/personas.js`, `core/cloud.js` | node types and edge kinds, the proposal format and its validator (validate, apply, status, what-if edits), personas, the cloud registry and its validator |
| Sync and validate | `core/derive.js`, `core/sync.js`, `core/validate.js` | the deriver contract (version 1), the sync plan, every check `validate` runs |
| The derivers | `plugins/starter`, `plugins/personas`, `plugins/cloud` | npm workspaces and imports; the personas file; the cloud registry with its detectors (hosts in code, Dockerfiles, images, CI workflows, a Caddyfile) |
| The house | `plugins/house/browser.js` | a live source over a house answer (a JSON file in the repo, or an API), a plain floor renderer, an HTTP permission checker |
| The server | `server/` | an allowlist, never a folder; the proposal routes; a strict Content-Security-Policy; a same-origin proxy for a source; loopback only |

| Shipping | `Dockerfile`, `compose.example.yml`, `.github/workflows/` | the image, CI (tests, gitleaks), the release (inert until switched on) |

Stage 1 differs from v1 in three ways: there is no sign-in (so loopback only), reviews are kept in the data folder (not posted to the PR; CF-06 ends that), and the Proposals menu reads proposal files from the checkout and the worktrees folder (not from spec PRs).

## 2. The decisions v1 builds (from the vision)

1. **Home** github.com/popcorn245/cornfield; npm `cornfield` and `@popcorn245/cornfield`; MIT.
2. **Packaging:** one buildless codebase; a Docker image on GHCR and an npm CLI; `cornfield.config.js` plus env.
3. **Backend:** its own server; forge sign-in (GitHub or Forgejo OAuth, admins are the repo's maintainers); a SQLite file for threads, reviews and pipeline state; forge adapters for issues, PRs, comments, checks and branches. No dependency on any repo's API: that is a plugin.
4. **Access:** nothing visible without signing in; admins only; a non-admin sees "this is the dev dashboard; ask a maintainer"; enforced on the server.
5. **Proposals and reviews:** proposals from pushed spec branches (the menu lists open spec PRs) and from the local worktrees folder; Approve / Send back posts a PR comment (a human line plus fenced JSON `{ verdict, note, edits }`); the latest comment wins; the agent reads it from the PR; no review file in a checkout.
6. **Actions:** approve / send back, land a green PR, re-run a failed check, the pipeline's own steps. Never force-merge, never deploy by hand, never touch anything live.
7. **Agents:** tracked through branches, spec PRs, PRs and checks; launching comes later.
8. **v1 scope:** the map and proposals, forge sign-in, PR-comment reviews, an issues and PRs panel for both forges. Threads, mockups, deploys, release notes and agent launching are [roadmap](../roadmap.md) issues.
9. **The house** is an optional, read-only plugin; no floor-plan editor.
10. **Generic logic here, a repo's facts in its config and plugins.**

## 3. Architecture

```
browser (explorer/)                         server/ (Node http, no framework)                    outside
-------------------                         ---------------------------------                    -------
main.js ── plugins.js ── sources ─────────▶ /cornfield/config.json, /repo/<module>.js
proposal.js, review.js ───────────────────▶ /proposals… ── reviews.js ── forge.js ── forge-github.js ──▶ GitHub
forge-panel.js (v1) ──────────────────────▶ /api/forge/…              └─ forge-forgejo.js ─▶ Forgejo
                                            auth.js (v1): OAuth, sessions, the admins-only guard on every route
                                            db.js (v1): node:sqlite in the data folder
                                            proxy.js: same-origin paths for a source's own API
CLI (cli/) ── core/ (derive, sync, validate, the formats) ── plugins/ (derivers)
```

- **The guard.** One function in `server/auth.js` runs before every route. No session: the sign-in page (and 401 for anything else). A session whose user is not a maintainer: the "ask a maintainer" page (and 403). The check asks the forge for the user's permission on the configured repo when the session starts, and again every 15 minutes.
- **Binding.** With sign-in configured (an OAuth app's id and secret in env, never in the config) and an `https` public URL, the server may bind beyond loopback; otherwise `server/bind.js` keeps refusing, as now.
- **Secrets** live in env only: `CORNFIELD_GITHUB_CLIENT_ID`, `CORNFIELD_GITHUB_CLIENT_SECRET` (or the Forgejo pair), `CORNFIELD_SESSION_SECRET`. The config names the forge, never a secret. Forge tokens are the signed-in user's own, kept in the session row, never sent to the browser.
- **SQLite.** `node:sqlite`, one file in the data folder, numbered migrations. Tables: `sessions`, `reviews` (a cache of the latest review per PR), `actions` (the audit of every action: who, what, when, the forge's answer), `forge_cache`.
- **Forge adapters.** One interface (`server/forge.js`): `me()`, `permission(repo, user)`, `issues(query)`, `pulls(query)`, `pullFiles(n)`, `comments(n)`, `comment(n, body)`, `checks(ref)`, `rerun(check)`, `merge(n, { onlyIfGreen: true })`, `branches()`, `file(ref, path)`. GitHub (REST v3) and Forgejo (v1 API) implement it; tests run against recorded answers and a fake server.
- **Proposals from spec PRs.** The menu lists open PRs that add or change files in the proposals folder; each is read at the PR's head commit. Worktree drafts stay as today.
- **Reviews.** `server/reviews.js` writes the comment (a human line, then a fenced block tagged `cornfield-review`) and reads the latest one by an admin. `cornfield review <slug>` reads it from the PR. Stage 1 reviews in the data folder are offered once as a comment on the matching PR, then left alone (renamed `.migrated`). The block's info string names the proposal (` ```cornfield-review <slug> `), because one PR can hold several; the JSON is exactly `{ verdict, note, edits }`. A draft in the checkout or a worktree has no PR, so it has no review: the explorer says to push it as a spec PR.
- **The panel.** `explorer/forge-panel.js`: issues and PRs, filters, links out. Selecting a PR asks for its files and checks; each file lights the node whose `file` holds it (the deepest one), and a failing check lights the test files it names.

## 6. Where the comments point

cornfield was extracted from the topology tool of a private monorepo, and its code comments keep the names of the design notes that tool was built from: **spec 0012** (the GPU map, proposals, scenarios, what-if edits and reviews), **spec 0029** (the physical world: machines, devices, rooms, personas, the live layer, permission checks) and **spec 0031** (the cloud registry, its detectors and outages), with work-item names like `TOPO-09`, `PHY-11` or `CLOUD-07`. Those notes are not public; what they decided is what the code and these docs now say. New work cites this repo's specs and issues instead.
